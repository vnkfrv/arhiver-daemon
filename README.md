# Архивация видеоконференций Talk

Демон, работающий нон-стоп: берёт из Контур.Толк записи конференций, «архивирует» их
(дословная расшифровка + улучшенная расшифровка + короткая выжимка + запись в БД),
уведомляет участников в **Tag (Mattermost)** и/или по **почте (SMTP)**, а по расписанию
удаляет видео из Толка. Тексты хранятся заданный срок (по умолчанию — бессрочно).

Логика во времени (по ТЗ):
- **Архивация — рано.** Демон транскрибирует записи и готовит тексты сразу (виден в
  модалке «Найти видеозапись»/«Скачать запись»).
- **Единоразовое уведомление о старом (old-records).** После того как весь бэклог записей
  старше `DELETE_VIDEO_AGE_DAYS` обработан, каждому участнику **один раз** приходит
  сообщение «старые видео переводятся в текст, у вас неделя скачать важное» с кнопкой.
- **Утилизация видео — поздно.** Через `DELETE_AFTER_NOTIFICATION` (grace, по умолч. неделя)
  после уведомления видео реально удаляется из Толка.
- **Очистка текстов — ещё позже.** Через `TEXT_RETENTION_DAYS` после удаления видео тексты
  удаляются. Если `TEXT_RETENTION_DAYS` не задан — тексты хранятся **бессрочно**.

Конвейер одной записи (машина состояний, идемпотентная):

```
transcribe → improve (LLM) → summarize (LLM) → save_to_db      (рано)
   → messages → delete            (когда видео старше порога и old-records разосланы)
   → cleanup_text                 (через TEXT_RETENTION_DAYS после удаления видео)
```

## Статусы записи

В поле `status` хранится код; расшифровку бот показывает админу в карточке записи.

| Код | Что означает |
|---|---|
| `NEW` | подхвачена из Толка, расшифровки ещё нет |
| `TRANSCRIBED` | готова базовая расшифровка (`_ASR`) |
| `IMPROVED` | готова улучшенная расшифровка (`_LLM`) |
| `SUMMARIZED` | готова выжимка (`_short`) |
| `SAVED` | тексты и участники сохранены, запись доступна в боте |
| `NOTIFIED` | участникам ушло уведомление об удалении, видео ждёт срока |
| `VIDEO_DELETED` | видео удалено из Толка, тексты хранятся |
| `TEXT_DELETED` | срок хранения текстов истёк, они удалены |
| `TOO_SHORT` | короче `MIN_DURATION` — не расшифровывается, удаляется при подхвате (что с видео на самом деле — в карточке записи) |
| `DELETE_PROTECTION` | Толк запрещает удалять видео — хранится бессрочно |
| `FAILED_ASR`, `FAILED_LLM`, `FAILED_SHORT`, `FAILED_SAVE`, `FAILED_NOTIFY`, `FAILED_DELETE`, `FAILED_CLEANUP` | стадия (транскрибация, LLM-правка, выжимка, сохранение, рассылка, удаление видео, очистка текстов) не удалась после всех повторов — запись ждёт решения админа |

## Что происходит при ошибках

- **Повторы по лестнице.** Упавшая стадия (любая) повторяется через 5 мин, 30 мин, 3 ч и
  23 ч — всё **от первой ошибки** (`RETRY_DELAYS_MIN`): второй повтор наступает через
  30 минут после ошибки, а не через 5+30. Если рабочее окно стадии к отметке закрыто,
  повтор выполняется при его открытии; пропущенные отметки не «догоняются» несколькими
  повторами подряд.
- **До решения админа.** Не помог и последний повтор (23 ч от первой ошибки) — запись
  получает статус `FAILED_<стадия>` (например `FAILED_LLM`) и стоит.
- **Сводка админам — раз в сутки.** В `ADMIN_REPORT_TIME` (по умолчанию 9:00) админам в Tag
  уходит ОДНО сообщение: сколько записей за сутки встало «до решения админа», с разбивкой
  по стадиям и примером ошибки на каждой, и с кнопкой перезапуска. Никто не встал —
  сообщения нет. Время — по часам демона (тем же, что и рабочие окна). Команда
  `restart_passed` (или кнопка в админ-панели) возвращает такие записи в работу — с того
  этапа, на котором они остановились.
- **Рассылка — исключение.** Если уведомление об удалении не дошло только до отдельных
  участников (нет в Tag, учётка деактивирована, нет почты), после тех же повторов демон идёт
  дальше, и видео удаляется по графику. Остальным участникам в самом уведомлении названы
  те, кто его не получил. Если же не получил никто и дело в связи (Tag лежит) — это поломка
  рассылки: запись встаёт «до решения админа», видео не удаляется.
- **Откуда берётся звук** — первый пригодный источник: 1) аудиоархив Толка, дорожки по
  спикерам; 2) тот же архив, общая дорожка (если дорожек спикеров нет); 3) сама видеозапись (если
  Толк не отдал архив или в нём нет ни одной дорожки). В 2) и 3) реплики не привязаны к
  участникам (`no_channels`), запись идёт по конвейеру как обычная, включая удаление видео.
- **Запись без аудио** (`no_audio`, терминально, видео не удаляется) — если звука нет нигде (видео
  тоже нет или в нём нет звуковой дорожки) либо в звуке не распознано ни слова. Сбой связи или
  непонятный ответ Толка «без аудио» не делает — это сбой стадии с повторами.
- **Пустой ответ LLM** — сбой стадии (повторы по лестнице), а не «готовая правка».
- **Самопроверки перед необратимым.** Уведомлять участников и удалять видео демон будет,
  только если расшифровка реально лежит на диске (иначе стадия падает и после повторов
  зовёт админа — так бывает, если том `Transcripts` не смонтирован). Прямо перед удалением
  строка записи перечитывается: если админ успел запретить удаление или удалил видео сам,
  демон уступает. Очистка текстов считается выполненной, только когда папки действительно нет.
- **Короткие записи.** Не удалось удалить при подхвате — повторы по той же лестнице; после
  неё видео остаётся в Толке, ошибка видна в карточке записи, удалить можно оттуда же.
  Если Толк запрещает удалять такую запись, её не трогаем вовсе.
- **Сбой базы.** Любая упавшая операция откатывается (соединение не «залипает»). Подхват
  новых записей при сбое базы прерывается и продолжается со следующего прохода с той же
  записи — пропустить её нельзя. Запись, обработка которой сорвалась целиком, берётся
  снова не раньше чем через 5 минут.
- **Участники.** Сбой Толка при получении профилей участников — сбой стадии сохранения
  (повторы): без почты человек не увидел бы запись в боте и не получил бы уведомление.
- **Нет дорожек по спикерам.** Распознаётся общая (сведённая) дорожка, запись помечается
  `no_channels` и идёт по конвейеру как обычная, включая удаление видео. В текстах реплики
  не привязаны к участникам (об этом строка в шапке файлов).
- **Запрет на удаление.** Толк запрещает удалять видео (`canBeRemoved=false`) — запись
  получает статус `DELETE_PROTECTION`, участников не уведомляем, больше её не трогаем (`FORCE_DELETE=1`
  отменяет запрет). Проверка идёт по свежим данным Толка перед рассылкой и перед удалением.
- **Видео уже нет в Толке** (удалили мимо архиватора) — запись просто помечается удалённой.

## Флаги поведения (вместо прежнего MODE)

Логика подхвата всегда одинакова (все записи из API, от старых к новым). Поведение
задают три независимых флага:

| Флаг | 1 | 0 |
|---|---|---|
| `REAL_DELETE` | реально удаляем видео из Толка | удаление **имитируем** (только лог); ручное удаление админом — всё равно настоящее |
| `SEND_TO_TAG` | шлём ЛС в Tag | заглушка в лог |
| `SEND_TO_MAIL` | дублируем уведомление на почту (SMTP) | не шлём |

«Сухой прогон» = все три флага в 0 (готовит тексты/БД, никого не трогает). Первый прогон
безопасен и без выключения флагов: демон сам сначала тихо наполняет бэклог, а
old-records-уведомления рассылает **один раз** после его завершения.

## Рабочие окна (ОБЯЗАТЕЛЬНЫ)

Демон работает ТОЛЬКО по временным окнам. Если окна не заданы — **не стартует** (пишет
ошибку и выходит). Формат ЧЧ:ММ, можно через полночь; `24:00` — то же, что `00:00`.
Некорректное время или срок (`TEXT_RETENTION_DAYS`, `DELETE_AFTER_NOTIFICATION`) — понятная
ошибка на старте, а не молчаливое значение по умолчанию.

- `TIME_START_ASR`/`TIME_END_ASR` — окно **транскрибации** (обычно шире, напр. 14:00–05:00).
- `TIME_START_LLM`/`TIME_END_LLM` — окно **LLM-обработки** (уже, напр. 00:01–05:00):
  improve/summarize + пост-стадии (БД, рассылка, удаление, очистка).
- Фоллбэк — общие `TIME_START`/`TIME_END` (одно окно на обе фазы).
- Окно проверяется **перед стартом каждой записи**; начатую стадию демон доводит до конца
  (не обрывает по `TIME_END`). Не успел за ночь — продолжит следующей (состояние в БД).

## Производительность

- **`RECORD_WORKERS`** независимых воркеров, у каждого своя запись (куски внутри —
  последовательно). Это же число = одновременных запросов к шлюзу. Больше → быстрее разбор.
  У каждого воркера свой `TalkClient`; БД и лимитер — общие; воркеры не пересекаются.
- **`ASR_LLM_RPM`** — лимит частоты запросов к MagnitGPT (ASR+LLM), скользящее окно 60с.
- **`RETRY_DELAYS_MIN`** — лестница повторов упавшей стадии: минуты от первой ошибки (по
  умолчанию `5,30,180,1380`); после неё запись ждёт решения админа (см. «Что происходит
  при ошибках»). Демон при этом не падает.
- **`ADMIN_REPORT_TIME`** — когда слать админам суточную сводку о таких записях (`09:00`).
- **Логи** ротируются (RotatingFileHandler). Каждая строка помечена `[воркер|запись]`;
  отдельный файл на воркер `logs/rec_N.log` + общий `logs/daemon.log`.
- **Ошибки в логах — одной строкой** (и у демона, и у бота): что не удалось, тип,
  сообщение и место в коде, например
  `доставка файла (…) не удалась — HTTPError: 503 … [bot.py:210 _deliver > mm_client.py:103 _request]`.
  Полные трейсбеки — `LOG_TRACEBACKS=1` (для отладки).
- **WebSocket бота** держит связь сам: при недоступном Tag переподключается каждые 5 с,
  в лог — первая потеря связи и дальше строка раз в минуту, затем «связь восстановлена».
  Сообщения обрабатываются в отдельном потоке, поэтому медленный ответ Tag не рвёт
  соединение (MM не закрывает его, не дождавшись ответа на ping).

## Установка и запуск

Рекомендуемый способ — Docker (см. **[DEPLOY.md](DEPLOY.md)**): два сервиса на одном образе.

Локально:
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить ключи и параметры
python main.py            # ДЕМОН архивации (бесконечно)
python main.py --once     # один проход и выход
python bot.py             # ИНТЕРАКТИВНЫЙ бот Tag
```
`ffmpeg` в образе ставится статическим бинарём из pip-пакета `imageio-ffmpeg` (apt не нужен).

**Быстрая сводка состояния** (только чтение, безопасно в рантайме):
```bash
python health.py     # или: docker compose exec talk-daemon python health.py
```

## Логика бота (Tag)

**Ботов два** — две учётки-бота в Tag, обе обслуживает один процесс `bot.py`:
- **основной** (`BOT_TOKEN`) — для участников записей: уведомления, меню, расшифровки;
- **админ-бот** (`ADMIN_BOT_TOKEN`) — для админов: панель, команды, суточная сводка, решения
  о составе админов. У админа тоже бывают свои записи, и так админская работа не смешивается
  в его личке с уведомлениями о них.

Если `ADMIN_BOT_TOKEN` не задан, админские функции остаются в основном боте. Если задан,
основной бот на админ-команду отвечает подсказкой, какому боту писать.

Боты отвечают ТОЛЬКО в ЛС. Эфемерные сообщения не используются: ответы — обычные посты,
ошибки заполнения форм показываются в самой форме.

### Основной бот

- **Любое сообщение боту** → меню: сколько записей пользователя в архиве и кнопки
  «Найти видеозапись» / «Поиск по названию».
- **«Найти видеозапись» / «Скачать запись»** → окно: выпадающий список ВСЕХ записей
  пользователя (сначала новые; в нём можно печатать для фильтра) + тип файла — «Базовая
  расшифровка» (`_ASR`) / «Улучшенная расшифровка» (`_LLM`) / «Краткая выжимка» (`_short`) /
  «Всё» (по умолчанию). Файл приходит в ветку с подписью `ДД.ММ.ГГГГ - Название - X мин.`.
  Видео пользователь скачивает из Толка сам. Если записей больше 1000, в список попадает
  1000 самых новых (окно Tag с бóльшим списком может не открыться) — остальные находятся
  поиском.
- **«Поиск по названию»** → окно: часть названия + тип файла. Одна находка — файл сразу;
  несколько — сообщение с выпадающим списком найденного (до 100, сначала новые), выбор
  присылает файл в ветку; ничего — ошибка прямо в окне.
- **Кнопки под уведомлением об удалении видео** → тексты этой записи в ветку.
- Тексты записи получит только её участник (сверка по почте) или админ.

### Админ-бот: панель и команды (в ЛС, только для админов)

Панель открывается командой `archiever_admin` или любым сообщением админ-боту.

**Суперадмин** один — `ADMIN_USERNAME` при первом запуске бота. Дальше он хранится в базе и
может **передать права** другому админу (сам остаётся обычным админом). Если изменить
`ADMIN_USERNAME` в `.env` и перезапустить бота, суперадмином станет указанный там — так
возвращают управление, когда суперадмин недоступен.

**Состав админов:**
- суперадмин добавляет и убирает админов сразу, остальных об этом не уведомляют;
- решение обычного админа вступает в силу через `ADMIN_CHANGE_DELAY_HOURS` (24 ч): всем
  админам приходит уведомление, суперадмин может решение **заблокировать** (кнопкой под
  уведомлением или в разделе «Админы»), подавший — отозвать. Об исходе узнают все админы;
- убрать суперадмина нельзя; решения админа, которого убрали, отменяются.

- `archiever_admin` — **админ-панель**:
  - сводка: сколько записей в каком состоянии, остановленные, удаления, окна, режим;
  - **«Найти запись»** — по ID, части названия или участнику; открывается **карточка**:
    дата, длительность, статус, участники, этапы, что с видео и текстами, ошибка;
  - из карточки: скачать любую расшифровку, **запретить / разрешить удаление**,
    **удалить видео** (с подтверждением), перезапустить запись, обновить;
  - разделы: остановленные «до решения админа» (с перезапуском всех), ближайшие удаления,
    неудаляемые; **админы** (добавить / убрать); **журнал** действий админов;
  - длинные ответы (разделы, результаты поиска, карточка) бот кладёт **в тред**: в личку
    приходит одна строка («Ближайшие удаления перечислены в треде к этому сообщению»), а
    содержимое и всё, что дальше делается с записью (файлы, ответы), — под ней. Пустой
    раздел — одной строкой, без треда.
- `restart_passed` — вернуть в работу все записи «до решения админа».
- `newadmin_{nickname}` — назначить админом (по тем же правилам, что и кнопкой).
- `remember_{ID}` — «хранить в Толке навсегда» (снять с авто-удаления).
- `delete_{ID}` — удалить видео вручную сейчас (любое, включая защищённое `remember`). Если
  видео уже удалено — бот ответит, когда и кем. Удаление настоящее и при `REAL_DELETE=0`
  (имитируется только автоматическое) — окно подтверждения об этом предупреждает.

Снятие запрета («Разрешить удаление») не удаляет видео сразу: участники получат новое
уведомление, и срок удаления отсчитывается заново.

## Раскладка на диске

Папки записей ШАРДИРОВАНЫ по дате (`ГГГГ/ММ`) — три файла на запись:

```
Transcripts/<ГГГГ>/<ММ>/<ID>/
    <ID>_ASR.md           # ДОСЛОВНЫЙ ASR (истина; LLM его не перезаписывает)
    <ID>_LLM.md           # LLM-обработанная расшифровка (может содержать баннер усушки)
    <ID>_short.md         # короткая выжимка
data/recordings.db        # SQLite: витрина + флаги стадий + планировщик + users + meta + журнал админов
logs/daemon.log           # логи (ротируются)
```

Дословный `_ASR.md` отделён от `_LLM.md` намеренно: любая LLM-правка может потерять текст,
поэтому оригинал распознавания хранится нетронутым. Если `_LLM` заметно короче `_ASR`
(порог `LLM_SHRINK_WARN_PCT`), сверху в `_LLM.md` пишется баннер о возможной потере.
Шапка (Название/Дата/Длительность/Участники) добавляется в начало всех трёх файлов.

**Планирование — в БД, без обхода файлов.** Всё состояние (флаги стадий, тайминги,
`done`/`next_due_at`) — в строке `recordings`. Демон берёт из БД только записи, которым
пора работать (`due_records` по индексу `(done, next_due_at)`). Поиск записей пользователя —
по индексу `participant(email)`.

> При обновлении со старой версии схема БД мигрируется автоматически (`ALTER` для новых
> колонок); новые таблицы (`users`, `meta`, `admin_log`) создаются на старте.

## Модули

- `talk_api.py` — клиент Толка (список/детали/`login→email`/аудио/видео/удаление) + `load_env`.
- `asr.py` — MagnitGPT_ASR: канал → mono WAV 16к → пословная расшифровка (ретраи, лимитер).
- `transcribe.py` — аудио → диалог по времени (реплики + слова); без дорожек по спикерам —
  общая дорожка, нарезанная на абзацы по паузам.
- `llm.py` — чат-LLM MagnitGPT (`/chat/completions`), детект обрыва по `finish_reason`.
- `enrich.py` — `improve_transcript` (правка) и `summarize_text` (выжимка); защита от усушки.
- `store.py` — файловое хранилище (`_ASR`/`_LLM`/`_short`, шардинг по дате).
- `db.py` — SQLite: витрина + флаги стадий + планировщик + `users`/`meta` + миграции.
- `statuses.py` — коды статусов, их расшифровки и названия стадий.
- `notify.py` — рассылка участникам (per-record и old-records) в Tag и/или на почту; кому
  не доставлено — возвращает пайплайну и называет в самом уведомлении.
- `mailer.py` — отправка писем по SMTP (получатель — параметр).
- `usersync.py` — наполнение таблицы `users` (имя из Тага, пропуск деактивированных).
- `mm_client.py` — клиент Tag (REST v4): ЛС, посты/файлы в ветку, модалки, кнопки и их подписи;
  клиент админ-бота.
- `bot.py` — оба бота в одном процессе (websockets + Flask): меню, выдача файлов, модалки,
  проверка прав и подписей; админские действия идут от имени админ-бота.
- `admin.py` — админ-панель: сводка, карточка записи, списки, операции админа.
- `pipeline.py` — стадии обработки одной записи + лестница повторов + гейтинг old-records +
  планирование.
- `config.py` — конфиг из `.env` (флаги, окна, лимиты, Tag, SMTP) с fail-fast.
- `main.py` — демон: подхват + параллельная обработка + суточная сводка админам + фазовая
  машина old-records.
- `texts.py` — все пользовательские строки (сообщения, кнопки, модалки) в одном месте.
- `logsetup.py` — логи с контекстом `[воркер|запись]` и ротацией.
- `ratelimit.py` — общий лимитер частоты запросов к шлюзу.
- `health.py` — read-only сводка состояния (для мониторинга в рантайме).

> Шлюз ASR/LLM (`llmlite.ai.corp.tander.ru`) и Talk — во внутренней сети; запускать
> нужно с хоста, откуда они резолвятся (см. [DEPLOY.md](DEPLOY.md)).
