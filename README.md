# Архивация видеоконференций Talk

Демон, работающий нон-стоп: берёт из Контур.Толк записи конференций, «архивирует» их
(дословная расшифровка + улучшенная расшифровка + короткая выжимка + запись в БД),
уведомляет участников в **Tag (Mattermost)** и/или по **почте (SMTP)**, а по расписанию
удаляет видео из Толка. Тексты хранятся заданный срок (по умолчанию — бессрочно).

Логика во времени (по ТЗ):
- **Архивация — рано.** Демон транскрибирует записи и готовит тексты сразу (виден в
  модалке «Найти видеозапись»/«Скачать запись»).
- **Единоразовое уведомление о старом (old-records).** После того как весь бэклог записей
  старше `DELETE_VIDEO_AGE_DAYS` обработан, каждому участнику **один раз** приходит
  сообщение «старые видео переводятся в текст, у вас неделя скачать важное» с кнопкой.
- **Утилизация видео — поздно.** Через `DELETE_AFTER_NOTIFICATION` (grace, по умолч. неделя)
  после уведомления видео реально удаляется из Толка.
- **Очистка текстов — ещё позже.** Через `TEXT_RETENTION_DAYS` после удаления видео тексты
  удаляются. Если `TEXT_RETENTION_DAYS` не задан — тексты хранятся **бессрочно**.

Конвейер одной записи (машина состояний, идемпотентная):

```
transcribe → improve (LLM) → summarize (LLM) → save_to_db      (рано)
   → messages → delete            (когда видео старше порога и old-records разосланы)
   → cleanup_text                 (через TEXT_RETENTION_DAYS после удаления видео)
```

## Флаги поведения (вместо прежнего MODE)

Логика подхвата всегда одинакова (все записи из API, от старых к новым). Поведение
задают три независимых флага:

| Флаг | 1 | 0 |
|---|---|---|
| `REAL_DELETE` | реально удаляем видео из Толка | удаление **имитируем** (только лог) |
| `SEND_TO_TAG` | шлём ЛС в Tag | заглушка в лог |
| `SEND_TO_MAIL` | дублируем уведомление на почту (SMTP) | не шлём |

«Сухой прогон» = все три флага в 0 (готовит тексты/БД, никого не трогает). Первый прогон
безопасен и без выключения флагов: демон сам сначала тихо наполняет бэклог, а
old-records-уведомления рассылает **один раз** после его завершения.

## Рабочие окна (ОБЯЗАТЕЛЬНЫ)

Демон работает ТОЛЬКО по временным окнам. Если окна не заданы — **не стартует** (пишет
ошибку и выходит). Формат ЧЧ:ММ, можно через полночь.

- `TIME_START_ASR`/`TIME_END_ASR` — окно **транскрибации** (обычно шире, напр. 14:00–05:00).
- `TIME_START_LLM`/`TIME_END_LLM` — окно **LLM-обработки** (уже, напр. 00:01–05:00):
  improve/summarize + пост-стадии (БД, рассылка, удаление, очистка).
- Фоллбэк — общие `TIME_START`/`TIME_END` (одно окно на обе фазы).
- Окно проверяется **перед стартом каждой записи**; начатую стадию демон доводит до конца
  (не обрывает по `TIME_END`). Не успел за ночь — продолжит следующей (состояние в БД).

## Производительность

- **`RECORD_WORKERS`** независимых воркеров, у каждого своя запись (куски внутри —
  последовательно). Это же число = одновременных запросов к шлюзу. Больше → быстрее разбор.
  У каждого воркера свой `TalkClient`; БД и лимитер — общие; воркеры не пересекаются.
- **`ASR_LLM_RPM`** — лимит частоты запросов к MagnitGPT (ASR+LLM), скользящее окно 60с.
- **`ASR_MAX_ATTEMPTS`** — после N неудач транскрибации (напр. битое аудио, на котором
  падает ffmpeg) запись помечается терминально статусом `ASR_FAILED` (ретраи прекращаются,
  ложный EMERGENCY не поднимается).
- **`EMERGENCY`** — если обработка «залипла» дольше N часов (напр. недоступен шлюз) —
  алерт админам в Tag. Демон при этом не падает: откладывает и повторяет.
- **Логи** ротируются (RotatingFileHandler). Каждая строка помечена `[воркер|запись]`;
  отдельный файл на воркер `logs/rec_N.log` + общий `logs/daemon.log`.

## Установка и запуск

Рекомендуемый способ — Docker (см. **[DEPLOY.md](DEPLOY.md)**): два сервиса на одном образе.

Локально:
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить ключи и параметры
python main.py            # ДЕМОН архивации (бесконечно)
python main.py --once     # один проход и выход
python bot.py             # ИНТЕРАКТИВНЫЙ бот Tag
```
`ffmpeg` в образе ставится статическим бинарём из pip-пакета `imageio-ffmpeg` (apt не нужен).

**Быстрая сводка состояния** (только чтение, безопасно в рантайме):
```bash
python health.py     # или: docker compose exec talk-daemon python health.py
```

## Логика бота (Tag)

- **ЛС боту** → help + кнопка «Найти видеозапись». Бот отвечает ТОЛЬКО в ЛС.
- **Кнопки уведомления**: «Базовая расшифровка» (`_ASR`) / «Улучшенная расшифровка»
  (`_LLM`) / «Краткая выжимка» (`_short`) / «Всё» → файл(ы) в ветку с подписью
  `ДД.ММ.ГГГГ - Название - X мин.`. Видео пользователь скачивает из Толка сам.
- **«Найти видеозапись» / «Скачать запись»** → модалка: select записи + select типа файла
  (Базовая/Улучшенная/Краткая/Всё). Если видео уже удалено — «Видеозапись была уже удалена😔».

### Админ-команды (в ЛС, текстом)

Первый админ — `ADMIN_USERNAME` (заносится в `admins` при старте бота).
- `newadmin_{nickname}` — назначить админом.
- `remember_{ID}` — «хранить в Толке навсегда» (снять с авто-удаления).
- `delete_{ID}` — удалить видео вручную сейчас (любое, включая защищённое `remember`).

## Раскладка на диске

Папки записей ШАРДИРОВАНЫ по дате (`ГГГГ/ММ`) — три файла на запись:

```
Transcripts/<ГГГГ>/<ММ>/<ID>/
    <ID>_ASR.md           # ДОСЛОВНЫЙ ASR (истина; LLM его не перезаписывает)
    <ID>_LLM.md           # LLM-обработанная расшифровка (может содержать баннер усушки)
    <ID>_short.md         # короткая выжимка
data/recordings.db        # SQLite: витрина + флаги стадий + планировщик + users + meta
logs/daemon.log           # логи (ротируются)
```

Дословный `_ASR.md` отделён от `_LLM.md` намеренно: любая LLM-правка может потерять текст,
поэтому оригинал распознавания хранится нетронутым. Если `_LLM` заметно короче `_ASR`
(порог `LLM_SHRINK_WARN_PCT`), сверху в `_LLM.md` пишется баннер о возможной потере.
Шапка (Название/Дата/Длительность/Участники) добавляется в начало всех трёх файлов.

**Планирование — в БД, без обхода файлов.** Всё состояние (флаги стадий, тайминги,
`done`/`next_due_at`) — в строке `recordings`. Демон берёт из БД только записи, которым
пора работать (`due_records` по индексу `(done, next_due_at)`). Поиск записей пользователя —
по индексу `participant(email)`.

> При обновлении со старой версии схема БД мигрируется автоматически (`ALTER` для новых
> колонок); новые таблицы (`users`, `meta`) создаются на старте.

## Модули

- `talk_api.py` — клиент Толка (список/детали/`login→email`/аудио/видео/удаление) + `load_env`.
- `asr.py` — MagnitGPT_ASR: канал → mono WAV 16к → пословная расшифровка (ретраи, лимитер).
- `transcribe.py` — аудио → диалог по времени (реплики + слова).
- `llm.py` — чат-LLM MagnitGPT (`/chat/completions`), детект обрыва по `finish_reason`.
- `enrich.py` — `improve_transcript` (правка) и `summarize_text` (выжимка); защита от усушки.
- `store.py` — файловое хранилище (`_ASR`/`_LLM`/`_short`, шардинг по дате).
- `db.py` — SQLite: витрина + флаги стадий + планировщик + `users`/`meta` + миграции.
- `statuses.py` — человекочитаемые статусы стадий.
- `notify.py` — рассылка участникам (per-record и old-records) в Tag и/или на почту.
- `mailer.py` — отправка писем по SMTP (получатель — параметр).
- `usersync.py` — наполнение таблицы `users` (имя из Тага, пропуск деактивированных).
- `mm_client.py` — клиент Tag (REST v4): ЛС, посты/файлы в ветку, модалки, кнопки.
- `bot.py` — интерактивный бот (websockets + Flask): кнопки, выдача файлов, модалка, админ.
- `pipeline.py` — стадии обработки одной записи + гейтинг old-records + планирование.
- `config.py` — конфиг из `.env` (флаги, окна, лимиты, Tag, SMTP) с fail-fast.
- `main.py` — демон: подхват + параллельная обработка + фазовая машина old-records.
- `texts.py` — все пользовательские строки (сообщения, кнопки, модалки) в одном месте.
- `logsetup.py` — логи с контекстом `[воркер|запись]` и ротацией.
- `ratelimit.py` — общий лимитер частоты запросов к шлюзу.
- `health.py` — read-only сводка состояния (для мониторинга в рантайме).

> Шлюз ASR/LLM (`llmlite.ai.corp.tander.ru`) и Talk — во внутренней сети; запускать
> нужно с хоста, откуда они резолвятся (см. [DEPLOY.md](DEPLOY.md)).
